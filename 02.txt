Cell 4: Reusable Auto Loader function

This is the most important cell in this notebook.

Python
from pyspark.sql import functions as F
 
def ingest_to_bronze(dataset_name, source_path, file_pattern, target_table):
schema_path = f"{STATE_ROOT}/{dataset_name}/schema"
checkpoint_path = f"{STATE_ROOT}/{dataset_name}/checkpoint"
 
# Auto Loader reads CSV files incrementally.
source_df = (
spark.readStream
.format("cloudFiles")
.option("cloudFiles.format", "csv")
.option("cloudFiles.schemaLocation", schema_path)
.option("cloudFiles.schemaEvolutionMode", "addNewColumns")
.option("cloudFiles.inferColumnTypes", "false")
.option("cloudFiles.rescuedDataColumn", "_rescued_data")
.option("header", "true")
.option("pathGlobFilter", file_pattern)
.load(source_path)
)
 
# Add ingestion metadata. No business transformations are performed.
bronze_df = (
source_df
.withColumn("_source_file", F.col("_metadata.file_path"))
.withColumn("_ingested_at", F.current_timestamp())
)
 
# Append to the Bronze Delta table and retain stream progress.
query = (
bronze_df.writeStream
.format("delta")
.outputMode("append")
.option("checkpointLocation", checkpoint_path)
.option("mergeSchema", "true")
.trigger(availableNow=True)
.toTable(target_table)
)
 
# Important for Workflow jobs: do not finish the notebook before ingestion ends.
query.awaitTermination()
 
print(f"PASS | Completed ingestion for {dataset_name}")
print(f" Target table: {target_table}")
 
Transcript

“This is the core ingestion logic of the notebook.

Instead of repeating almost identical Auto Loader code three times, we created one reusable function called ingest_to_bronze.

The function accepts four parameters: dataset name, source path, file pattern, and target table.

First, we create separate schema and checkpoint locations for each dataset.

Then we use spark.readStream.format("cloudFiles"), which enables Databricks Auto Loader.

cloudFiles.format is CSV because our source files are CSV files.

cloudFiles.schemaLocation provides Auto Loader a persistent location for tracking the discovered schema.

cloudFiles.schemaEvolutionMode is set to addNewColumns, allowing Auto Loader to detect newly introduced source columns.

cloudFiles.inferColumnTypes is false, so Auto Loader does not attempt to infer each CSV column's data type here. This is suitable for our Bronze design because we want to preserve the raw source representation and handle business-level typing later.

_rescued_data is configured as the rescued-data column. If Auto Loader encounters values or fields that cannot be placed into the expected schema, that information can be preserved there rather than simply being lost.

header=true tells Spark that the first row contains the column names.

pathGlobFilter ensures that each ingestion stream reads only files matching that dataset's filename pattern.

After reading the source, we add two metadata columns. _source_file records where each record originated using _metadata.file_path, while _ingested_at captures the ingestion timestamp.

We then write the DataFrame as Delta using writeStream. outputMode("append") means new records are appended to the Bronze table.

Each stream gets its own checkpoint location. The checkpoint records streaming progress and is what helps prevent already committed files from being processed again on subsequent runs.

mergeSchema=true allows the destination Delta table to accept schema additions after Auto Loader detects new source columns.

Finally, availableNow=True tells the stream to process the currently available data and then stop rather than run continuously.

awaitTermination() makes the notebook wait until that ingestion stream has completed before proceeding.”

Critical difference: schemaLocation vs checkpointLocation

Memorize this because an SME can definitely ask.

schemaLocation

“Schema location tracks information about the source schema detected by Auto Loader.”

checkpointLocation

“Checkpoint location tracks the stream's processing progress so Auto Loader knows what it has already processed.”

Easy memory trick:

Schema location = what does the incoming data look like?

Checkpoint = how far has ingestion progressed?

addNewColumns vs mergeSchema

Another important counter-question.

“cloudFiles.schemaEvolutionMode="addNewColumns" handles newly discovered columns on the Auto Loader/source side.

mergeSchema="true" allows those additional columns to be accepted by the destination Delta table.”

So remember:

Auto Loader input → addNewColumns

Delta output → mergeSchema

The notebook itself notes that a newly detected source column can cause the current run to stop with a schema-evolution exception, after which a workflow retry can restart using the evolved schema.

Cell 5: Table and checkpoint safety check
Python
def path_has_files(path):
try:
return len(dbutils.fs.ls(path)) > 0
except Exception:
return False
 
def check_table_checkpoint_state(target_table, checkpoint_path):
table_exists = spark.catalog.tableExists(target_table)
checkpoint_has_files = path_has_files(checkpoint_path)
 
table_has_rows = False
if table_exists:
table_has_rows = spark.table(target_table).limit(1).count() > 0
 
if table_has_rows and not checkpoint_has_files:
raise RuntimeError(
f"Safety stop: {target_table} contains data, but its checkpoint "
f"is missing or empty: {checkpoint_path}. Do not restart ingestion "
"with a new checkpoint until the state has been investigated."
)
 
if checkpoint_has_files and not table_exists:
raise RuntimeError(
f"Safety stop: checkpoint data exists at {checkpoint_path}, "
f"but target table {target_table} does not exist. Investigate "
"the table/checkpoint state before proceeding."
)
 
print(
f"PASS | State check for {target_table} "
f"(table_exists={table_exists}, "
f"table_has_rows={table_has_rows}, "
f"checkpoint_has_files={checkpoint_has_files})"
)
What to say

“This cell introduces an important safety check between the Bronze Delta table and its checkpoint.

path_has_files() checks whether the checkpoint path contains any files.

Then check_table_checkpoint_state() checks three things: whether the target table exists, whether it contains records, and whether checkpoint information exists.

If the Bronze table already contains records but the checkpoint is missing, we stop the process. Otherwise, starting ingestion with a new checkpoint could cause previously processed files to be treated as new and create duplicate ingestion.

We also check the opposite situation. If checkpoint data exists but the target table is missing, the checkpoint and Delta table are inconsistent, so we also stop ingestion.

The purpose is to fail safely rather than silently continue with an inconsistent ingestion state.”

SME: Why .limit(1).count() instead of .count()?

Good answer:

“We only need to determine whether at least one row exists. We don't need the total row count for this particular validation.”

Cell 11: Expected rerun behavior

This final Markdown section is also important because SME may ask what happens the second time the job executes.

Present it like this:

“One of the main advantages of this design is rerun behavior.

If we execute the notebook again without adding new files, Auto Loader uses its maintained state and should not ingest the already committed files again.

If new CSV files arrive, they are discovered and appended to the corresponding Bronze Delta table.

If a new source column appears, Auto Loader's addNewColumns schema-evolution behavior can update its tracked schema. The current run may stop with a schema-evolution exception, and our workflow retry can restart using the updated schema.

If incoming data cannot fit the expected schema, we can investigate _rescued_data.

Most importantly, we should not delete or change the checkpoint just to force reruns, because the checkpoint represents ingestion progress and changing it can result in previously processed files being ingested again.”

The notebook recommends a Workflow with maximum concurrent runs of 1, 2 retries, and a 1-minute minimum retry interval after manual testing.

Top SME counter-questions you should memorize
1. What exactly is Auto Loader?

“Auto Loader is the Databricks file ingestion mechanism used here through cloudFiles. It incrementally discovers and processes new files while maintaining ingestion state.”

2. Why readStream if this job eventually stops?

“Because Auto Loader uses Spark Structured Streaming APIs for incremental file ingestion. availableNow=True tells the stream to process the currently available files and then terminate instead of continuously waiting for future files.”

3. What is availableNow=True?

“Process everything currently available, then stop.”

New file tomorrow → next job execution processes it.

4. What does awaitTermination() do?

“It makes the notebook wait until the current availableNow stream finishes. Without this wait, the notebook could continue before the ingestion query has completed.”

5. What does checkpoint store?

“It stores streaming progress and helps Auto Loader determine what has already been processed.”

6. What does schema location store?

“It maintains Auto Loader's tracked source-schema information.”

7. What is _rescued_data?

“It is used to retain data that Auto Loader cannot place into the expected schema, which helps prevent problematic information from simply being discarded.”

8. If _rescued_data is NULL for every row, what does it mean?

“For those rows, Auto Loader did not need to place any incompatible or unexpected data into _rescued_data.”

It does not mean all other columns have no nulls.

That's an important distinction.

9. Is deduplication happening?

“No. We deliberately preserve the Bronze source data. This notebook does not perform business-record deduplication.”

10. Is CDC implemented here?

“No. CDC is not implemented in this notebook.”

11. Is there a watermark?

“No. We aren't using event-time watermarking in this notebook. Our file-processing progress is managed through the Auto Loader streaming state and checkpoint.”

12. Why append?

“Bronze is preserving incoming records. As newly discovered files arrive, their records are appended rather than replacing previously ingested Bronze data.”

13. Why separate checkpoints?

“Each dataset is an independent ingestion stream. Separate checkpoints prevent the processing state of flight schedules, flight movements, and weather observations from interfering with one another.”

14. What happens if the same old file remains in the source folder?

“Auto Loader uses its maintained state to identify previously processed files, so simply leaving an already committed file in the source location should not cause it to be ingested again on the next normal execution.”

15. What if you delete the checkpoint?

“We should not do that casually. The checkpoint represents ingestion progress. Starting an existing Bronze table with a new checkpoint can cause previously processed files to be treated as new and create duplicate ingestion. That is exactly why this notebook contains the table/checkpoint safety check.”

Cell 4: NULL profiling
Python
null_results = []
 
for dataset, df in dataframes.items():
total_rows = df.count()
 
if total_rows == 0:
for column_name in df.columns:
null_results.append((dataset, column_name, 0, 0.0))
continue
 
expressions = [
F.sum(F.when(F.col(column_name).isNull(), 1).otherwise(0))
.alias(column_name)
for column_name in df.columns
]
 
counts = df.agg(*expressions).first().asDict()
 
for column_name in df.columns:
null_count = int(counts[column_name] or 0)
null_percent = round((null_count / total_rows) * 100, 2)
 
null_results.append(
(dataset, column_name, null_count, null_percent)
)
 
null_profile = spark.createDataFrame(
null_results,
["dataset", "column_name", "null_count", "null_percent"]
)
 
display(
null_profile
.filter(F.col("null_count") > 0)
.orderBy("dataset", F.desc("null_count"))
)
Transcript

“Next, we perform column-level null profiling across every dataset.

For each DataFrame, we determine its total number of rows.

Then, for every column, we use isNull() to identify null values and aggregate their count.

Once the counts are available, we calculate the null percentage as null count divided by total rows multiplied by 100.

We create null_profile, containing the dataset, column name, null count, and null percentage.

For easier analysis, the final display shows only columns having at least one null and orders them by their null count.

Importantly, we don't automatically classify every null as a data-quality defect. Profiling tells us where nulls exist. Whether that is actually invalid depends on whether the business considers that particular field mandatory or optional.”

Cell 5: Business-key profiling
Python
key_results = []
 
for dataset, details in TABLES.items():
df = dataframes[dataset]
key_column = details["key"]
 
if key_column not in df.columns:
raise RuntimeError(
f"Expected business key '{key_column}' is missing "
f"from {details['name']}."
)
 
total_rows = df.count()
 
null_keys = df.filter(F.col(key_column).isNull()).count()
 
distinct_keys = df.select(key_column).where(
F.col(key_column).isNotNull()
).distinct().count()
 
duplicate_key_values = (
df.where(F.col(key_column).isNotNull())
.groupBy(key_column)
.count()
.filter(F.col("count") > 1)
.count()
)
 
duplicate_key_rows = (
df.where(F.col(key_column).isNotNull())
.groupBy(key_column)
.count()
.filter(F.col("count") > 1)
.agg(F.sum("count"))
.first()[0]
) or 0
 
key_results.append((
dataset, key_column, total_rows, null_keys, distinct_keys,
duplicate_key_values, int(duplicate_key_rows)
))
 
key_profile = spark.createDataFrame(
key_results,
[
"dataset", "business_key", "total_rows", "null_key_rows",
"distinct_non_null_keys", "duplicate_key_values",
"rows_with_duplicate_keys"
]
)
 
display(key_profile)
Transcript

“This is one of our key data-quality profiling checks.

For every dataset, we first verify that its expected business-key column actually exists.

We then calculate the total rows and count how many records have a null business key.

Next, we calculate the number of distinct non-null business keys.

After that, we group records by business key and identify keys whose count is greater than one.

duplicate_key_values tells us how many unique key values are repeated.

rows_with_duplicate_keys tells us how many total records belong to those repeated-key groups.

Again, we are only reporting duplicate business keys here. We are not deleting records or deciding which record should survive.”

Cell 6: Exact duplicate rows
Python
exact_duplicate_results = []
 
for dataset, df in dataframes.items():
if not df.columns:
exact_duplicate_results.append((dataset, 0))
continue
 
grouped_rows = (
df.groupBy(*[F.col(column_name) for column_name in df.columns])
.count()
.filter(F.col("count") > 1)
)
 
extra_copies = (
grouped_rows
.select(F.sum(F.col("count") - 1).alias("extra_copies"))
.first()["extra_copies"]
) or 0
 
exact_duplicate_results.append((dataset, int(extra_copies)))
 
exact_duplicate_profile = spark.createDataFrame(
exact_duplicate_results,
["dataset", "extra_exact_duplicate_rows"]
)
 
display(exact_duplicate_profile)
Transcript

“Here we distinguish duplicate business keys from exact duplicate rows.

We group the DataFrame using every column. Therefore, records are considered exact duplicates only when all column values are identical.

For groups occurring more than once, we calculate count - 1.

We subtract one because the first occurrence is considered the original record, while only the additional copies are counted as extra duplicates.

For example, if one identical row occurs three times, 3 - 1 gives two extra duplicate copies.

The important distinction is that two records may have the same business key but different values in other columns. In that case, they are duplicate business keys but not exact duplicate rows.”

Best one-line answer

“Business-key duplicate means the identifier repeats; exact duplicate means the complete row repeats.”

p50 = percentiles[1] if len(percentiles) > 1 else None
p75 = percentiles[2] if len(percentiles) > 2 else None
 
numeric_results.append((
dataset, column_name, stats["minimum"], stats["maximum"],
stats["average"], p25, p50, p75
))
 
numeric_profile = spark.createDataFrame(
numeric_results,

"dataset", "column_name", "minimum", "maximum", "average",
"p25", "p50_median", "p75"

Transcript

“This cell performs numeric profiling.

We first define the numeric attributes that are important for each dataset.

Each selected value is cast to double for profiling purposes. This does not modify the original Bronze table.

We calculate minimum, maximum, and average values.

We then use approxQuantile() to calculate the 25th percentile, median or 50th percentile, and 75th percentile.

The final output enables us to understand the normal range and distribution of numerical values and helps us identify potentially unusual extremes for further investigation.”

Memorize P25/P50/P75

P25: approximately 25% of observations are at or below this value.

P50: median. Approximately 50% are at or below it.

P75: approximately 75% are at or below it.

The 0.01 in your code is the relative error parameter used by approxQuantile().

The cell does two different checks: timestamp parsing and chronological relationships.

Main transcript

“Next, we profile timestamp quality.

We define the timestamp columns we want to inspect and use to_timestamp() to attempt to parse each one.

We specifically count records where the original value is non-null but the parsed value becomes null. Those represent non-null values that could not be interpreted as timestamps.

Cell 10: Referential integrity and orphan records

This is another very important SME cell.

Transcript

“Next, we validate referential integrity between operational datasets and their related reference datasets.

We define a reusable function called check_reference_coverage.

The source column represents a foreign key, while the reference column represents the corresponding key in the reference dataset.

We separately calculate null foreign keys and orphan foreign keys.

A null foreign key means that the source doesn't contain an ID for that record.

An orphan foreign key means that an ID exists in the source, but that ID cannot be found in the corresponding reference dataset.

To identify orphans, we use a left_anti join. This returns source values that do not have a matching value in the reference dataset.

We apply this check to schedule-airline, schedule-aircraft, schedule-airports, movement-flight, movement-airport, and weather-airport relationships.

Finally, we display how many source rows were checked, how many foreign keys were null, and how many were orphaned.”

Example you should memorize

Suppose:

Plain Text
source_rows_checked = 603
null_foreign_keys = 0
orphan_foreign_keys = 0

Say:

“All 603 source rows were checked. None had a null foreign key, and none of the non-null IDs were missing from the referenced dataset.”

SME: Why left anti join?

“Because a left anti join returns records from the left side that have no matching record on the right side, which makes it suitable for identifying orphan foreign keys.”
